# NeonPlan 3D local development and Home Assistant deployment

## Repository and local workflow

- This is the `neonplan3d` Home Assistant custom integration. Its version is in `custom_components/neonplan3d/manifest.json`.
- The frontend is Lit/TypeScript with Three.js, built by `frontend/build.mjs`; generated bundles are committed under `custom_components/neonplan3d/frontend/`.
- On Windows, use Node.js/npm, Python, Git, and OpenSSH (`ssh.exe`, `scp.exe`). Install frontend dependencies with `npm ci` in `frontend/`. The dedicated Home Assistant Ed25519 key is `%USERPROFILE%/.ssh/homeassistant`; set `NEONPLAN_SSH_KEY` to its external path if needed. `NeonPlan.Dev.psm1` enforces batch auth, strict known-host checking, and the pinned server fingerprint; it never prompts for or stores a password.
- Import `scripts/NeonPlan.Dev.psm1` in PowerShell. Commands: `Build-NeonPlan`, `Test-NeonPlan`, `Test-NeonPlanRemote`, `Compare-NeonPlanRemote`, `Backup-NeonPlan`, `Deploy-NeonPlan`, `Restore-NeonPlan`, `Restart-NeonPlan`.
- Build runs npm install from lockfile, typecheck, and production bundle build. Tests run frontend tests/typecheck and pytest.
- Keep generated frontend bundles in sync with source when changing the frontend.

## Remote safety procedure

- First run `Test-NeonPlanRemote`, `Compare-NeonPlanRemote`, and `Backup-NeonPlan`. These use SSH read-only inspection or create/download an integration-only backup; no Home Assistant restart is part of them.
- `Deploy-NeonPlan` must be explicitly invoked with `-ApproveRemoteWrite`. Review the version comparison, remote drift, and completed backup first. The script uploads to a unique temporary staging folder and copies only local integration files into matching paths. It never deletes remote-only files, floor plans, configuration, entities, furniture packs, `.storage`, or anything outside the integration directory. It verifies copied hashes.
- This downstream adds a trusted pack key in `packs.py`; therefore `Deploy-NeonPlan` also refuses deployment until `.local/hacs-source.txt` records a verified nonofficial `owner/repository` after HACS is switched to the TechPanda fork. Do not create that marker until the HACS repository source has actually been verified. The marker is a local gate, not a remote HACS setting. Do not install an official HACS update over the custom integration; update through the downstream branch workflow instead.
- A deployment alone does not restart Home Assistant. Restart only after explicit user approval, using `Restart-NeonPlan` (or `Deploy-NeonPlan -ApproveRemoteWrite -ApproveRestart` when both approvals have already been explicitly given). The command asks the operator to type `RESTART HOME ASSISTANT` and calls `ha core restart`, the Supervisor-managed CLI mechanism. Do not restart the Docker container directly.
- Rollback requires `Restore-NeonPlan -Backup <archive> -ApproveRemoteWrite`. It restores only `custom_components/neonplan3d/` from an integration-only archive. A restart after rollback is separately gated by `-ApproveRestart` and typed confirmation.
- Never modify unrelated Docker containers, system packages, other integrations, Home Assistant storage, or configuration. Never use the repository's existing `npm run deploy` against this server: `scripts/deploy.mjs` deletes target files absent from the source and is intended for disposable test targets.
- The user must explicitly approve remote writes and restarts. Do not deploy or restart merely because scripts have been prepared or checks pass.
